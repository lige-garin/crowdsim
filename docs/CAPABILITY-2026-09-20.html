04本轮最重要的发现：多楼层的真相

我上一轮写的 ADR 是错的，已重写。初版说「没有任何图元知道自己在哪层」，据此提议给 schema 加楼层——那次搜索只看了 world 和 crowdMovement.ts 就停了。第二次搜索发现 schema 早就支持了。

实际是三层状态，弄清楚之后，工作量比原先判断的小得多：

层次 状态 证据
场景 schema · 已提交 基础已就位 scene.floors[] + floorSchema（每层自带 id / name / level / elevationMeters 和自己的 world）已存在； 4 个 schema 带裸 floorId——底图、分区、地块、店铺，都是零售方向的图元，不是为楼层而加
楼层 stage 1 · 进行中未提交 正在写 sceneFloors.ts + sceneEditorFloors.ts（23:13–23:15，注释标注 "ADR-0010, stage 1"）：floorId 统一到 10 类图元，编辑器获得 activeFloorId 与 addFloor/setActiveFloor，一次画一层。 两模块都写明自己不是什么——「连接件是 stage 2，尚不存在；这里的一层是可以画、可以看的东西，不是人能去的地方」
多楼层运行时 孤儿 multifloorScene.ts 已有 MultiFloorScene{floors, connectors}、VerticalConnector.kind: "elevator"|"escalator"|"stairs"、flattenMultiFloorScene。只被自己的测试引用
仿真引擎 单层 router 只建一张二维场；SimulationAgent 无层号——不同楼层同一平面坐标的两者在社会力看来肩并肩；38 个文件读 world.width/height
结论：这不是「设计多楼层」，是「把已有的数据模型接上运行路径」。 五个具体缺口：① agent 加 floorId；② 逐层路由 + 连接件成边；③ 把 VerticalConnector 放进运行路径（它现在活在孤儿模块里）；④ 编辑器切层 UI；⑤ 逐层渲染。

其中一个决定要先做：multifloorScene.ts 要么提上来当引擎的加载入口，要么按已有的孤儿规则删掉——留着是唯一不允许的选项，因为读者看到 VerticalConnector 会合理地以为扶梯已经建模了。
