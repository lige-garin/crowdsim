# 选址沙盘：定位与执行计划

- 状态：**已确认的定位**（2026-10-05），**第一场景改为商场内部**（同日补充）。
  本文件是中文的，给人看的；仓库里那份英文的 `docs/adr/0034-...` 是技术决策记录。
  两者内容会随时间分叉，冲突时以本文件的定位为准，以 ADR 的技术细节为准。
- 一行代码都还没写。

## 一、定位

**开店 / 落位前的沙盘推演。不是选址评分，不是客流预测。**

用户把「我想开一家 320 平、客单价 85、6 个双人桌 + 10 个四人桌 + 4 个六人桌

- 2 个十人包房的中餐厅」摆进去，系统告诉他这个布局跑起来是什么样：
  排队堵不堵、翻台几次、桌型配比合不合理、门开在哪儿顺不顺。

商场场景同理：把珠宝区和美妆区对调，看动线怎么变、冷区能不能带热；
选 A 铺位还是 B 铺位，看各自能接到多少路过的人。

### 核心原则（最重要的一条）

> **相对比较可信，绝对数值不可信。**

周边 POI → 客流这条链上至少有四步没有任何实测依据
（POI 数量→人口、人口→日来客数、日来客数→15 分钟分时、竞品→分流），
caidian 那套系数（780 户 / 2.7 人 / 560 名写字楼员工）是拍的，没有标定过。

所以：

- ❌ 不卖「预计午市 120 人」——这数字错了会让人赔几十万租金。
- ✅ 卖「A 布局比 B 布局排队短 40%」——即使绝对人数是错的，这个相对结论仍然成立。

所有推断出来的数字都要在 `docs/CLAIMS_LEDGER.md` 登记为**未标定**，
界面上也要写明，不能只写在文档里。

## 二、为什么第一场景改成商场

补充需求：商场内区域经常调换（珠宝区和美妆区对调），
以及商户选定某个铺位后算仿真。

**这不是一个附加场景，它比街边店更适合当第一场景。** 理由按重要性排：

### 1. 边界封闭——街边店最致命的那个问题在商场里不存在

街边店最难的是「人怎么来的」：3 公里范围内的人开车、坐地铁、骑电动车过来，
而模型**没有开车 / 公交 / 地铁这三种方式**。这是个真实的能力缺口。

商场是封闭域：人只能从**入口、扶梯口、电梯口**进来。
这些点是**真实存在的、可枚举的注入边界**，不需要编造到达方式。

→ **街边店的核心难题，在商场里自动消失。**

### 2. 天然可对比——正好落在我们唯一能站得住的地方

街边店选址是**单点决策**，没法做 A/B。

商场是天然对照：

- 珠宝区 ↔ 美妆区对调：调前 vs 调后。
- A 铺位 vs B 铺位：同一个商户、同一个业态、只换位置。

这完美契合「相对比较可信，绝对数值不可信」这条原则。
我们不需要说对绝对人数，只需要说清楚两个方案的差别。

### 3. 重复付费，不是一锤子买卖

开一家街边店只选一次址。商场的业态规划和品牌落位**每年都在调**。
重复决策 >> 一次性决策。

### 4. 付费方明确，而且有预算

商场运营方 / 招商团队 / 商业地产 / 第三方策划咨询公司。
（边界猎手公开的客户列表里就写着开发商、品牌商、商业招商、设计机构、
第三方策划咨询公司。）

### 5. 最容易拿到真实数据——这是唯一能补上护城河的地方

很多商场**自己就有**闸机、红外客流计数、会员系统数据。
这是把「推断」变成「标定」的唯一途径。街边店没有这种数据。

### 6. 现有 schema 天生就是为商场建的

这一条是硬证据，不是推测：

| 商场需要的东西  | CrowdSim 现状                                                                                            |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| 珠宝区 / 美妆区 | `zoneCategorySchema` **已有 `jewelry`、`cosmetics`**，还有 anchor / atrium / corridor / dining / fashion |
| 多层            | `floorSchema`：`level` + `elevationMeters`                                                               |
| 扶梯（单向）    | `connectorSchema`：`kind = stair \| escalator \| elevator`，**扶梯单向**是内建语义                       |
| 电梯轿厢限载    | `connectorSchema` 有轿厢载客上限、共享井道数量                                                           |
| 设备故障场景    | `hazardSchema` 有 `escalatorOutage`、`elevatorOutage`                                                    |
| 铺位            | `storeLotSchema`：门位置、排队锚点、门脸 `frontage`                                                      |
| 店铺与品牌      | `shopSchema` + `brandProfileSchema` + `shopFronts` 渲染                                                  |

**街边店场景上面这些东西一个都用不上。**
另外 ADR-0029（电梯连续乘降与负载均衡）、ADR-0030（安检 / 闸机优先通道与分叉）
本来就是商场和枢纽场景的 ADR。

### 7. 商场是室内，连投影层都不需要

室内平面本来就是米制，**不需要 GCJ-02、不需要 Overpass、不需要地图选点**。
街边店那条链上最麻烦的三样东西，商场一步都不用碰。

### 一个要提前说清的规模问题

大型购物中心周末峰值同时在场可能上万，超过现有 2000 上限。
但**「调区」和「选铺位」本来就是局部问题**——只需要细算那一层那一区
加相邻动线，几百人足够。全商场多层同时细算是另一个更大的需求，排在后面。

→ 所以商场场景同样**不需要先抬人数上限**。

## 三、执行步骤：共 8 步

**前 3 步是商场场景，且零外部依赖**——不需要地图、不需要投影层、
不需要改 schema、不需要接任何 API。做完就能演示、就能拿去跟商场运营方谈。

| 步    | 做什么                                                | 产出                            | 依赖            |
| ----- | ----------------------------------------------------- | ------------------------------- | --------------- |
| **1** | 商场骨架生成器：楼层 + 分区 + 扶梯 / 电梯 + 铺位      | 一个多层商场场景                | 无              |
| **2** | 铺位内布局：店铺表单 → 店内场景（桌位 / 门 / 排队区） | 铺位内部场景                    | 第 1 步         |
| **3** | 仿真 + 对比报告：铺位 A/B、调区前后                   | **核心卖点**                    | 第 2 步         |
| **4** | 商场自有客流数据接入（闸机 / 计数器 / 会员）          | **标定机会**                    | 第 3 步         |
| **5** | caidian POI：商场周边，决定「进商场多少人」           | 到达率                          | 可与第 1 步并行 |
| **6** | 投影层（为街边店做准备）                              | 经纬度 → 米制 + GCJ-02 ↔ WGS-84 | 可并行          |
| **7** | 街边店：地图选点 + OSM 周边建筑                       | 街边场景                        | 第 6 步         |
| **8** | L1 中观层：300 米–3 公里路网流量注入                  | 3 公里真正被建模                | 第 7 步         |

### 第 1 步：商场骨架生成器

输入：几层、每层有哪些分区（珠宝 / 美妆 / 餐饮 / 主力店 / 中庭 / 走廊）、
扶梯和电梯在哪、切多少个铺位。
输出一个 `CrowdSimScene`：floors + zones + connectors + storeLots。

- 全部落在已有 schema 上，`jewelry` / `cosmetics` 这些分区业态枚举现成就有。
- 现成可复用的：`packages/app/src/editor/storeLotGeneration.ts` 的
  `generateStoreLotsForZone` 已经在做「品牌档案 + 店铺 + 铺位」三件套。
- **验证**：给定一份商场描述，断言楼层数、分区数、连接器方向（扶梯单向）、
  铺位门与排队锚点位置；做退回验证。

### 第 2 步：铺位内布局

店铺表单（名称 / 面积 / 客单价 / 桌型 / 业态）→ 铺位内部的墙、桌位、门、排队区。

字段落点**全部已有，不用改 schema**：

- 名称 → `shop.name`
- 面积 → `shop.size.{width,height}`（需定一个默认长宽比）
- 客单价 → `brand.priceTier`（1–5 档，需写一张"元 → 档位"对照表）
- 桌型 → `shop.capacity` = `2n₂ + 4n₄ + 6n₆ + 10n₁₀`
- 业态 → `brand.category = "restaurant"`（枚举里已有）
- 桌型原始数字 → `shop.customParameters`

需要新增的只有一个：`shop.dwellMeanSeconds` 的正餐停留时长区间，
**必须标出处**。

### 第 3 步：仿真 + 对比报告

四项指标：路过人数、进店人数、排队长度、停留时长。
两套方案并排对比 —— **这是产品的核心卖点，也是"相对比较可信"的落点**。

- 铺位 A/B：同业态、同参数，只换位置。
- 调区前后：珠宝区 ↔ 美妆区对调，看动线和冷区变化。
- **验证**：改一个变量（把门挪到另一侧、减两个六人桌、对调两个区），
  断言指标变化方向符合预期。

### 第 4 步：商场自有客流数据（这一步是护城河）

商场通常有闸机 / 红外计数器 / 会员数据。接进来做两件事：

1. 校准入口和扶梯口的注入率（不再是推断值）。
2. **拿真实客流做回归** —— 这是把「推断」升级成「标定」的唯一途径。

只要有一家商场愿意给数据，整条链就闭环了；没有的话，
就永远只能停在"相对比较"这一层。

### 第 5 步：caidian POI

商场周边的小区 / 写字楼 / 学校 / 公交 / 地铁站，
用来决定「一天有多少人进这个商场」。
caidian 现有的 `fetchAllLayers` 和 `calculateScore` 已经能算。
系数未标定，必须在账本登记。

### 第 6–8 步：街边店那条链

投影层 → 地图选点 + OSM 周边建筑 → L1 中观层（3 公里）。
这三步是街边店场景，排在商场之后，因为商场先跑通能更快验证定位。

### 第 8 步（L1 中观层）结论：暂缓不建

详细评估见 `docs/adr/0035-mesoscopic-catchment-layer.md`。一句话：

> 卡住 3 公里的不是算力，是稀疏。而 L1 能回答的两个问题，
> 一个用实测数据回答更好（门开哪边 = 每个门的分时计数），
> 另一个我们已经用未标定系数在做了（竞品分流），
> 换模型不会让任何结论更可信。

触发条件（满足任一则重启）：拿到至少两个门的分时真实客流；或客户明确
要求竞品分流的绝对数字且接受误差区间。

### 第 9–13 步：把能力接到界面上

第 1–8 步做出来的全是**能力层**：`createMallSkeleton`、`planShopLayout`、
`measureScenario`、`calibrateArrivals`、`importSiteBundle` 各有测试，但全仓
grep 下来**生产调用方为零** —— 只有测试在用。要变成用户能用的东西还要五步：

| 步  | 做什么                                                                    | 状态                                      |
| --- | ------------------------------------------------------------------------- | ----------------------------------------- |
| 9   | 选址入口：编辑器「文件 → 导入选址包」，选 caidian 导出的 bundle，生成场景 | **已完成**（2026-10-06）                  |
| 10  | 店铺表单页面：名称 / 面积 / 客单价 / 桌型 → `planShopLayout`              | **已完成** 10-07 面板「店铺布局」         |
| 11  | 方案管理：同一场地两套方案，选一对跑 A/B                                  | **已完成** 10-07「方案对比」A/B 存档位    |
| 12  | 对比报告页：显示 `describeComparison` 的中文行，首行带免责声明            | **已完成** 10-07 同一面板，免责为报告首行 |
| 13  | caidian 仓库加「导出为 CrowdSim」按钮（跨仓库）                           | **已完成** 10-07（caidian 未提交）        |

**第 13 步的两条硬边界**，写在这里免得以后被当成疏漏补掉：

- caidian 只有 POI 点，**没有建筑轮廓、没有门位**，所以导出的包里也**没有**
  `siteGeometry`。编一个门位会让仿真看起来有依据，而那个依据是假的。
- `coefficientsAreCalibrated` 恒为 `false`：caidian 的 analysisService 系数全是
  自拟值，没有拿真实客流回归过。

所以这个包能给 CrowdSim 的是「会有多少人到店」这条曲线，不是「店长什么样」。
导入后楼和门要用户自己画 —— 导入报告里会直接写「请在编辑器里放置」。

第 9 步不发网络请求：bundle 从本地选中的文件读入，所以 README 里「默认构建
无网络请求」的承诺仍然成立。粘贴地址自动取周边那种做法要调地图 API，会打破
这个承诺，除非明确要，否则不做。

### 第 14 步：修这一轮接出来的五个 BUG（2026-10-07）

第 9–13 步把能力接上了界面，接的时候带了五个 BUG 进来。按严重度：

| 严重度 | BUG                                | 触发路径                                                      |
| ------ | ---------------------------------- | ------------------------------------------------------------- |
| P0     | 0 桌的店应用后 `parseScene` 抛异常 | 导入选址包 → 打开「店铺布局」→ 直接点应用（最短路径）         |
| P0     | 客单价 0 把价位档 3 静默改成 1     | 同上；空输入框被当成 0 元，`writeLayout` 的守卫被绕过         |
| P1     | 换场景后表单串到新店               | 两个 live 面板注册时漏了 `key={scene.id}`                     |
| P1     | caidian `distance` 不是米          | 环带按 500/1000m 切分，但那个字段在人口密度层里是 1..100 的分 |
| P2     | `revokeObjectURL` 同步调用         | Firefox / Safari 上点了没反应                                 |

前两条的共同点值得记下来：**能力层已经有守卫，界面层没把「没有值」和「值是0」
分开传下去**。`writeLayout` 早就用 `averageTicketYuan === undefined` 区分
「用户没说」和「用户说了 0」，面板却永远传一个数字，把守卫绕了过去。所以修法
不是加新守卫，是让界面把「没填」如实传成 `undefined`。

P1 的 caidian 那一侧：`PoiItem.distance` 不是距离 —— 后端只给人口密度图层填它，
而那个值是密度指数。所以环带改成从 `location` 的经纬度自己算（haversine），
不再读那个字段。这条不影响当前仿真结果（`demandInference` 只读 `count`，不读
`ringCounts`），但字段留着不改，下次谁读了它就会踩。

### 第 15 步：新建项目流程（2026-10-07，产品方向转向后）

选址包路线退役（见本文件上面的「产品方向转向」），第一屏改成项目列表，
下面是新建一个项目的三步。

| 步  | 做什么                                                       | 文件                                                    |
| --- | ------------------------------------------------------------ | ------------------------------------------------------- |
| 1   | 项目列表：新建 / 打开 / 复制 / 删除，本地 localStorage       | `projects/projectStore.ts` · `projects/ProjectList.tsx` |
| 2   | 地图选点：高德底图点选，或直接填经纬度 + 半径                | `projects/MapPlacement.tsx`                             |
| 3   | 项目表单：类型 / 类目 / 面积 / 楼层数 + **平面从哪来四选一** | `projects/ProjectDetailsForm.tsx`                       |

**平面四选一，各自产出什么写在选项的说明里**：

| 来源       | 产出                                                                |
| ---------- | ------------------------------------------------------------------- |
| 自己画     | 进编辑器逐段画墙。什么都不会自动生成                                |
| DXF / IFC  | 抽墙体和轮廓。**门洞认不出来**，门要自己补                          |
| 按楼层生成 | `createMallSkeleton` 真的生成墙、店铺、扶梯、首层门。扶梯位置是猜的 |
| GLB        | **只有外观，不产生墙体** —— 人可以在模型里走，仿真不知道墙在哪      |

**三条硬边界**：

1. **地图 key 未配置时流程仍然走通**。经纬度能手填，因为坐标是选址真正需要的，
   地图只是帮你挑位置用的。没有 key 的构建不该卡在这一步。
2. **面积和楼层数只被记录，不用来自动生成墙体**。楼层数不是平面图；按楼层数
   长出来的墙看起来像勘测过的，而它不是。
3. **`GLB 那一格必须标「仅外观」**。schema 认 `glb` 是渲染资产（`sceneModelAssets.ts`
   拿 `GLTFLoader` 加载），它不产生 `walls`。不标的话用户以为碰撞算过了。

坐标一律 GCJ-02（高德本身用的就是它）。换 WGS-84 会在沈阳偏 570 m，
项目会跟周围的楼错位，而这种错位在界面上看不出来。

**还没做的**：POI 实时查询（等高德 key）、平面图落位（截图那条路线刻意不做——
照片估出来的轮廓会让仿真看起来有依据而依据是假的）。

## 四、现在不做

- **全商场多层同时细算** —— 峰值人数会超 2000，需要抬上限并依赖 GPU 路径
  （GPU 实测 10 万人 0.45 毫秒/步，CPU 回退仍是 2000）。排在后面。
- **桌级服务行为**（点单 / 上菜 / 翻台）—— 新的个体行为，单独决策。
- **抬 `crowdBudget` 上限** —— 局部仿真几百人，2000 够用，需要时再说。
- **百度 / 美团数据源** —— 百度开放平台的热力图是渲染图层不是数据接口，
  真数据在百度地图慧眼（商业授权，需申请审批）。只留适配器接口。
- **门能不能关** —— 会影响 schema 和 ADR-0025，单独决策。

## 五、真正的护城河

不是仿真引擎，是**真实客流数据**。

商场场景最大的价值不只是它好做，而是**它是唯一能拿到真实数据的场景**。
谁有闸机计数、会员数据来回归，谁才能把「推断」变成「标定」。

第一版的胜负手不是做得多准，
**是能不能找到一家商场愿意拿他们的真实客流数据来做回归。**
找到，这条链才闭环；找不到，就永远只是"看起来科学"。
