## 三、P0 阻断级缺陷（10 条）

### 【安全】P0-1 后端所有数据接口零鉴权，完整 IDOR

`backend/src/index.ts:144-237, 294-350` —— 只有 `/api/auth/session` 和 `/logout` 校验 token。`GET|POST /api/projects`、`PUT /api/projects/:id/scene`、`GET /api/usage/:ownerId`、artifact 读写**全部不校验 session**；`ownerId`/`actorId` 直接取自请求体（`readString(body,"ownerId")`）。
**触发**：`curl GET /api/projects` 枚举全部项目；`PUT /api/projects/<他人id>/scene` 覆写他人场景。
**佐证**：`backendClient.ts:65-77` 的 `send()` 也完全不带 `Authorization` 头——不是客户端漏传，是服务端根本没实现。
**修复**：`routeRequest` 顶部统一解析 session；`ownerId`/`actorId` 一律取自 session；对 `:projectId` 校验归属。

### 【安全】P0-2 会话 token 是 32 位 FNV-1a 哈希

`backend/src/auth.ts:70-82` —— `token = "csess_" + fnv1a32(accountId + "|" + ISO时间戳)`。攻击者知道 accountId 后枚举登录时间即可离线算出 token；整个空间只有 2³²，且 `sessions.set(token, …)` 用 token 作 key，约 6.5 万会话时有 50% 生日碰撞概率 → **B 用户登录后拿到 A 的会话**。
**修复**：`crypto.getRandomValues` 生成 ≥128 位随机 token，与 accountId 解耦。

### 【安全】P0-3 AI 代理与 Google Tiles 代理无鉴权无限额，直接烧付费密钥

`backend/src/index.ts:248-289, 352-394` —— AI 路由只过滤"客户端密钥"，然后把调用方**完全可控的 payload**（model / max_tokens / system / messages）原样转发到 `api.anthropic.com`，附带服务端 `x-api-key`。tiles 同理，无需任何凭据。
**后果**：任何第三方把你的后端当免费 LLM/地图网关，直接产生账单。
**修复**：两条路由强制 session + 接入 `recordUsage` 限额 + model/max_tokens 白名单 + 速率限制。

### 【正确性】P0-4 `bidirectional` 入口导致 agent 出生即消失（已实测复现）

`simulationEngine.ts:128-142` —— `bidirectional` 同时进 sources 和 sinks；出生 jitter `|Δ| ≤ width/2` 恰好等于 sink 半径，且首步决策还没跑（每 6 步一次），`lifecycleState` 为 undefined → `:387` 的到达判定恒成立。
**实测（60 步）**：

```
单个 bidirectional 入口 :  spawned 11  exited 11  alive 0
对照组 source+远处 sink :  spawned 11  exited 0   alive 11
```

**后果**：空城；且 `exitedCount`/吞吐量指标**全部造假**（agent 存活 1/60 秒就计入 exited）。
**修复**：spawn 时排除同 id entrance 作为 sink；新生 agent 打初始 `lifecycleState="walk"`；第 0 步先跑一次决策。

### 【渲染】P0-5 视口每秒销毁重建整个 Three 场景 + 重新 `requestDevice()`，并泄漏 GPUDevice

`SimulationViewport.tsx:134` effect → `:653` 依赖数组 `[bioCityVisualSecond, crowdScene, heatmapCells, viewMode]`。`heatmapCells` 来自 `App.tsx:116-122` useMemo，其上游 `App.tsx:242-263` 每 1 秒 `setHeatmapSamples` → **引用每秒变一次**。
该 effect 内部：新建 Scene/几何/材质 → `requestAdapter` → `requestDevice` → `renderer.init()` → `seedAgents()` 循环 10 万次 → `benchmarkRenderer()` **同步渲 45 帧** → 重建约 2000 个 Mesh。
cleanup（`:631-653`）只有 `renderer?.dispose()`，**从不调 `device.destroy()`**。
**后果**：每秒一次完整 GPU 上下文重建 + **每秒泄漏一个 GPUDevice** + 一次阻塞式 benchmark；相机状态靠 ref 打补丁才没被重置（代码注释里已承认）。长跑必然 GPU 资源耗尽、标签页崩溃。
**修复**：GPU/Three 初始化只依赖 `[viewMode, crowdScene.id]`；heatmap/昼夜改成 **imperative 更新**（改已有 mesh 的 material/light）；cleanup 显式 `device.destroy()`。

### 【渲染】P0-6 每帧绘制 10 万实例，只为显示 240 个人

`SimulationViewport.tsx:179-183` 以 `performanceAgentCount = 100_000` 构造 InstancedMesh，`updateAgentInstances`（`:465-492`）只更新前 N 个矩阵、**从不设 `agents.count`**。
**后果**：GPU 每帧 100,000 × 24 = **240 万次顶点着色**（阴影 pass 再来一遍），99.76% 是 scale=0 的退化实例；同时 `instanceMatrix.needsUpdate = true` 每帧**全量上传 6.4 MB**（≈384 MB/s 带宽）。
**修复**：`agents.count = visible`；`instanceMatrix.addUpdateRange(0, visible*16)`；容量按实际上限分配。

### 【渲染】P0-7 渲染上限被 240 卡死，与 HUD 数字不符

`useSimulationWorkerController.ts:232-234` `readSimulationSharedAgents(sharedMemory, **240**)`，而 SAB 容量是 2000，HUD 打印的是 `snapshot.agentCount`（可到 2000）。
**后果**：HUD 说 1800 人，视口画 240 个。三个数字（实例化容量 100,000 / 仿真上限 2,000 / 实际可见 240）**差 400 倍**。
**修复**：提到 SAB 容量并直接把 `Float32Array` 视图喂给实例矩阵，跳过中间 JS 对象数组。

### 【UX】P0-8 场景编辑器的编辑结果永远进不了仿真——产品核心闭环是断的

`SceneEditor.tsx:114-122`（props 里**没有任何 `onSceneChange` 回调**）· `AppStage.tsx:141-145`（只往下传不往上收）· `App.tsx:55,60`（两个仿真控制器都硬绑 `demoScene`）· `useSimulationWorkerController.ts:29,68`（scene 只在 init 用一次）。
**用户感受**：花 20 分钟画墙、放 6 家店、调吸引力和容量，点"开始"——跑的还是那个雨天商业街，改动一个字节都没进仿真。唯一出口是导出 `.csim.json`，然后没有然后。
**后果**：整个 2.5D 编辑器和上百个参数字段全部失去意义。
**修复**：`scene` 状态提升到 `AppContent`；编辑器加显式「**应用到仿真 / 用此场景重跑**」主按钮（隐式同步会导致每落一个图元就重启仿真）。

## 五、P2 清单（择要）

**渲染**
