## 二、本轮新发现（此前 3 份 REVIEW 和 ledger 均未记录）

### P0-1｜`arrivalCalibration.ts` 整个模块是孤儿，而 CHANGELOG 把它当已交付能力宣传

**位置**：`packages/app/src/analytics/arrivalCalibration.ts:79,180,216`；宣传文案在 `CHANGELOG.md:71`

三个导出函数全部零生产调用方。实测 grep（已排除模块自身与测试文件）返回**空**。
测试有 12 个，**全绿**。

矛盾点在于这个模块自己的注释（`arrivalCalibration.ts:6-8`）：

> 这是站点仿真中唯一可以被**测量**而非推断的输入……门上装了客流计数器的东西不是猜测。

而 `panelRegistry.tsx` 中**无任何门禁客流面板**，`grep arrivalCalibration docs/CLAIMS_LEDGER.md` = **0 次命中**（ledger 从未记录这个孤儿）。

**实际后果**：用户导入真实门禁客流数据时，跑的仍是 `demandInference.ts` 里自带的 `uncalibrated` 系数。产品宣称「可实测」的唯一路径不可达，而 CI 全绿。

对照组证明标准是清晰的：同一次提交里真正接了线的 `measureScenario` → `LayoutComparePanel.tsx:125`、`createMallSkeleton` → `sceneForNewProject.ts:85` 都能在生产代码里找到调用方。

### P0-2｜每个仿真 tick 深拷贝全部 agent，2000 人时约 35 MB/s 的对象 churn

**位置**：`packages/app/src/engine/simulationEngine.ts:615-644`（`makeSnapshot`）

`SimulationAgent` 实测 **38 个字段**。`makeSnapshot` 对全体 agent 做 `.map()` 展开 + 一次 `.reduce()`。

**实测成本**（本机真跑，50 次取中位）：

| agent 数 | 中位耗时 | p95      | 单次分配 | 60Hz 折算 |
| -------- | -------- | -------- | -------- | --------- |
| 500      | 0.027 ms | 0.105 ms | 148 KB   | 8.7 MB/s  |
| 1000     | 0.056 ms | 0.183 ms | 297 KB   | 17.4 MB/s |
| 2000     | 0.110 ms | 0.311 ms | 594 KB   | 34.8 MB/s |

`makeSnapshot` 由 `tickAsync`（`:1322,1340`）在**每个 tick** 调用一次。
文件顶部 `:387-392` 自记的「2000 agents = 4.2 ms/step」**只测了 `stepCrowd`，没算 `makeSnapshot`**。

**这条要修正一个容易得出的错误结论**：不能说「worker 路径下这份数据没人要」。
`postSnapshot`（`simulation.worker.ts:217-227`）把整个 snapshot 对象交给 `postMessage`，
结构化克隆本身会再深拷贝一次 agents，主线程**确实收到**。
渲染端 `selectCrowdAgents`（`agentInstanceField.ts:78`）在 overlay 无数据时会回退到 `snapshot.agents`。

真实成本是**两层**：引擎内 `.map()` 一次 + postMessage 结构化克隆一次，2000 人时每 tick 两遍 594 KB。
p95 是中位的 2.8 倍，说明 GC 压力下抖动明显——这才是掉帧的实际来源。

**定级说明**：CPU 时间本身只有 0.11 ms，不构成瓶颈；**P0 指的是「最该优化的点 + 架构越界」**，
因为 `makeSnapshot` 是渲染关注点却住在引擎里，且每 tick 无条件全量重算。

### P1-1｜GPU↔CPU 对拍测试（9 个）在 CI 结构性永不执行

**位置**：`core-gpu/src/index.test.ts:61`（4 个）、`neuralResidualGpu.test.ts:81`、`app/src/engine/gpuCrowdBackend.test.ts:24`（4 个）

模式统一为 `const gpuTest = maybeNavigator?.gpu ? it : it.skip`。
Node/jsdom 下 `navigator.gpu` 恒为 undefined → 实测 core-gpu `84 passed | 5 skipped`。

README 与 ledger 已诚实记录此约束，**这不是隐瞒**。但结论是：
「GPU 与 CPU 逐步对拍」在 CI 里是**零保护**，GPU 路径的正确性目前只靠人工真机跑。

### P1-2｜`createSceneFromDxf` 是可绕过全部披露逻辑的旁路，且零测试

**位置**：`packages/app/src/editor/dxfImport.ts:77`

UI 和测试**只用** `createSceneFromDxfWithReport`。这个 30 行薄封装零调用方零测试，
一旦有人 future-call 它，会静默丢掉 `importGeometry` 的报告/披露逻辑。
建议删除或加 `@deprecated` 标注，而不是留着。

### P1-3｜determinism 测试覆盖的路径 ≠ 生产默认路径

**位置**：断言在 `simulationSceneUpdate.test.ts:59-67` / `simulationEngine.test.ts:225-229`（同步 `step()`）；
生产在 `simulation.worker.ts:203`（`tickAsync`）。

两者在 cpu-compat 下共享 `advanceAgentsCpu`，**CPU 路径结论可迁移**，注释也没夸大。
但两点未覆盖：

1. **GPU 路径 `advanceAgentsGpu`（`simulationEngine.ts:1092-1139`）零 determinism 覆盖**。
   GPU 有浮点原子累加 + spatial hash 排序，是顺序依赖高风险区；
   而 `gpuParityScenarios.ts` 测的是「结果相近」，不是「同 seed 逐位可复现」。
2. `step(900)` 连跑 900 步**只调 1 次** `makeSnapshot`，真实 rAF 下每 delta 至少 1 次。
   **高频 `makeSnapshot` 路径从未被 determinism 测试触及**——与 P0-2 是同一个洞的两面。

### P1-4｜`App.tsx` 无条件构建两个完整仿真引擎

**位置**：`packages/app/src/App.tsx:94-103`

主线程与 worker 两个 controller 都无条件调用，用 `usesWorkerSimulationPath` 选活跃者。

**已核实这不是「两个仿真同时跑」**：未选中的引擎 `status` 停在 `paused`，
`useSimulationController.ts:83-86` 的早退使它的 rAF 循环不启动。这一层是安全的。

但**场景派生成本是双份的**：`createSimulationEngineFromScene` → `deriveSceneGeometry`
→ `createMallCrowdDecisionBackend`（32 KB，含路由图、墙索引、决策后端）在每次场景编辑时**跑两遍**。
